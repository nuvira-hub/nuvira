# NuviraHub — Security model (summary)

[← Index](README.md)

- Every device generates its own key pair at first start; the private key never leaves the device and is kept protected by the system: Windows DPAPI, the macOS Keychain, the Secret Service or systemd-creds (TPM 2.0 when present) on Linux, the file's permissions only where the system offers nothing better ([36](36-device-key.md)).
- The server only knows: ID, public key, presence, session metadata (who/when/how long). **Never** contents.
- Sessions are TLS 1.3 end-to-end between the two devices' keys (D10); the session password travels only inside that channel and is checked by the agent (D13). Planned: unattended password checked with a **PAKE** (OPAQUE/SPAKE2), so that it does not travel at all, not even encrypted.
- Wrong passwords (temporary and permanent, through the server) are limited by the agent, in memory (they start again when the agent restarts): after 5 wrong passwords from one viewer ID that ID is refused for 1 minute, doubling with each further wrong one up to 15 minutes, and forgotten 10 minutes after its last wrong password or the end of its lock; after 20 wrong passwords in 10 minutes on the computer, from any IDs, only viewers that already gave a right password since the agent started are let in, until those wrong passwords are 10 minutes old. A refused attempt is answered like a wrong password (the viewer is not told it is locked, also when it gives the right password), without checking the password (no PBKDF2) and without the 2-second pause, so it frees its place at once. Someone guessing with new IDs therefore cannot lock out a technician who already connected, but a technician new to this computer may be refused while the attack lasts: the allowed IDs of the access rules ([42](42-access-rules.md)) are the real protection of unattended access. Empty passwords are not counted. Two-factor codes keep their own lock (5 wrong in 10 minutes). Each checked wrong password still waits 2 seconds before the connection closes. Not yet: a warning to the person at the PC. Tried on Windows (unit and end-to-end tests); not tried on Linux and macOS, where the code is the same (review lot 3: AGT-4).
- Before the viewer has authenticated, the agent waits at most 10 s for each step of the handshake (the control stream in LAN mode and switch sides, the viewer's `Hello`, then its password; the confirmation by the person at the PC, 30 s, and the two-factor code, 3 minutes, keep their own waits), accepts messages of at most 64 KiB on the control stream (16 MiB after authentication; 64 KiB on the input stream), and writes at most 64 characters of the viewer's device name, system and version to its log. A connection that has not authenticated does not make the computer busy, so knowing the ID is not enough to keep other viewers out: at most 8 sessions through the server may wait for their password at once (more are told the computer is busy), and of two viewers connecting together the first whose credentials are right gets the session, the other is told the computer is busy (review lot 2: AGT-1, AGT-2, AGT-3, NET-3).
- The server proves each device's key at registration (a signature of a random nonce) and refuses the small-order Ed25519 keys, with which no private key is needed (review lot 8: SRV-6). Protection of a server open to anybody ([deploy/README.md](../deploy/README.md#limits-per-address)): a connection must register within 10 s; per address (IPv4, IPv6 /64) at most 256 connections at once, 30 registrations a minute (burst 100) of which 10 a minute (burst 100, per IPv6 /48) may be keys never seen, 10 connection requests a minute (burst 15), 2,048 presence IDs a minute (burst 4,096), 64 WebSocket connections of 10,000 datagrams a second each; devices registered and never seen again are removed after 30 days; blocks of devices, addresses and networks (`nuvira-server block`). Local addresses are exempt unless `NUVIRA_RATE_LIMITS=all` (review lot 8: SRV-7, SRV-8, SRV-9, SRV-14).
- Always-visible indicator of an active session on the remote PC, which cannot be turned off in attended mode.
- Signed automatic updates (Ed25519) distributed by your own server.
- Address book sign-in (Pro server, app and web console; review lot 5: PRO-4), limited in memory (the counters start again when the server restarts): after 5 wrong passwords for one account from one address that account is refused from that address for 1 minute, doubling with each further wrong one up to 15 minutes; after 20 wrong passwords from one address, for any accounts, the whole address is refused the same way (IPv6 addresses count per /64; several people behind one public address share that counter). There is no lock of an account alone, so a stranger cannot lock out an account by its name: from another address it signs in as usual. A counter is forgotten 10 minutes after its last wrong password or the end of its lock. Two-factor codes: after 5 wrong codes (they can only be tried after the right password) the account's codes are refused for 10 minutes without being checked, also a right one; the administrators get the usual alarm and can reset the password. A refused attempt is answered "too many wrong attempts" (HTTP 429 in the console), without checking the password; each checked wrong password or code waits 1 second. A missing account costs the same password check as an existing one (no user enumeration by timing), and at most as many password checks as CPU threads run at once (the others wait). An app connection that stays open re-reads its sign-in at every request: a logout elsewhere, a new password or a deleted account sign it out at once, and a changed role applies at once (PRO-3).
- Address book (D16): account passwords hashed with Argon2id; device passwords encrypted with AES-256-GCM using a server key kept next to the database; remembered sign-ins are random tokens stored only as SHA-256.
