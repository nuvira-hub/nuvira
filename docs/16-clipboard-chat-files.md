# NuviraHub — Clipboard, chat and files

[← Index](README.md)

Last part of phase 2 (Windows MVP).

## Shared clipboard (text and images)

During the session text and images copied on one of the two PCs can be pasted on the other, in both directions and with no commands.

- `client/clipboard` (`nuvira-clipboard`, arboard library): one thread per side checks the clipboard every 400 ms. It reads the clipboard only when a counter says something was copied: the sequence number on Windows (`GetClipboardSequenceNumber`), the pasteboard's `changeCount` on macOS, the CLIPBOARD owner changes (XFixes) in an X11 session; then it compares the content with the last one (the same text copied again is not sent again). On Wayland, and on X11 without XFixes, it still reads and compares the content at every check (Wayland: a native Wayland program's copy is not guaranteed to change Xwayland's selection, which is what the counter watches). Before 2026-11-20 (review lot 23, VWR-6) Linux and macOS read the whole clipboard at every check: with a 1080p image in it about 15 ms (11 ms of CPU) every 400 ms for the whole session, on whichever side had it.
- New text travels on the control channel (`ControlMessage.clipboard`, at most 1 MB) and the other side writes it to its clipboard. Received text is not sent back.
- Only what is copied during the session counts: content already present at start-up is not sent.
- The agent shares it only if it can control the PC (not with `--view-only`). As SYSTEM, in the user's session, it uses the user's clipboard (it belongs to the `winsta0` window station).

Test of 2026-10-27: NUC ↔ PC-LABORATORIO (service agent), copy and paste in both directions, tested by the user.

Images (2026-10-27): copied images travel as PNG (fast compression, at most 8192x8192 pixels and 32 MB) on their own unidirectional stream, like files (`FileChunk.clipboard_image`), so a large image does not hold up the control channel; echo is avoided with a hash of the pixels. Tested by the user between the NUC and PC-LABORATORIO in both directions (2026-10-27).

## Chat

Text chat between the person in control and the person using the PC.

- Protocol: `ControlMessage.chat` on the control channel, in both directions.
- Viewer: speech-bubble button in the bar; the panel (`chat.html`) is a second WebView on the right, under the bar. It opens by itself when a message arrives. While it is open the keyboard is used for typing; a click on the image gives it back to the session.
- On the controlled PC the chat is in the NuviraHub app, in the chat section next to the session strip: an incoming message brings the app to the front with the cursor in the reply field. It works with the app's agent and with the service's (`chat` events and `chat` command on the local channel, see [14-phase3-service.md](14-phase3-service.md)).
- The chat stays visible in the app after the session closes, until the next session. It is not saved.
- The command-line agent, without the app, writes received messages to the log.

Test of 2026-10-27: a message from the NUC arrived in the app on PC-LABORATORIO (service), the reply from there arrived in the viewer's panel.

## Sending files to the remote PC

First version, chosen with the user: the person in control sends files to the remote PC. The full two-way file manager will come later.

- **Viewer**: drag files onto the session window, or use the bar's "Send file" button (file dialog, rfd library, on its own thread). Files are sent one at a time. In the bar, in place of fps and latency, the progress appears, then the outcome, which also stays in the chat panel. For tests: `--send-file FILE` sends as soon as connected.
- **Protocol**: each file has its own unidirectional QUIC stream, opened by the viewer after the input stream. The first `FileChunk` carries name and size, the following ones the data (256 KB each); the end of the stream closes the file. The agent replies with `ControlMessage.file_received` (outcome and folder, or the reason for the error).
- **Agent** (`client/agent/src/files.rs`): saves to the logged-in user's Downloads folder. As SYSTEM (service) it gets it from the session user's token (`WTSQueryUserToken` + `SHGetKnownFolderPath`); with no user logged in it refuses the file. It first writes `name.part` and renames it only if the size matches; if the name exists it adds " (1)", " (2)"…; it keeps only the last part of the name, without folders or invalid characters, without the invisible characters that change the direction of the text (U+202E and the like, which can make `evil<U+202E>txt.exe` look like `evilexe.txt`), with "_" in front of a name Windows reserves for a device (`CON`, `NUL.txt`, `COM1`...), and at most 200 bytes (a short extension is kept). It stops as soon as more than the announced size arrives. As SYSTEM every step on the Downloads folder (create, write, rename, delete) runs impersonating that user, as in the file manager below: the folder is the user's (profile, `User Shell Folders`, possibly a junction), so SYSTEM never writes there with its own rights (review AGT-15, Phase 6 lot 1). With `--view-only` it accepts no files.
- **On the controlled PC** the app notifies in the chat panel ("You received the file … in the Downloads folder") and comes to the front.

Tests of 2026-10-27, NUC → PC-LABORATORIO (service agent):

- random 20 MB file in about 0.7 s (about 230 Mbit/s in a LAN), identical SHA-256 on both PCs;
- a second send of the same file saved as "name (1).bin"; the file written by SYSTEM inherits the permissions of the Downloads folder, so the user has full control over it (since the review's lot 1 the file is written as the user);
- drag and drop and the "Send file" button tested by the user.

## File manager (both directions, resumable)

The "File" button of the toolbar (shown when the agent says it supports it, `Hello.file_manager`) opens a second window (`client/viewer/src/filemanager.rs` and `filemanager.html`): this PC on the left, the remote one on the right, starting from known folders (Desktop, Documents, Downloads) and drives. Select files (Ctrl+click for several), open a folder on the other side, then "Send →" or "← Download". Transfers are listed at the bottom with their progress; an interrupted one has "Resume".

- **Protocol** (`session.proto`): `FsRequest` on the control channel (`list`, `download` from an offset, `upload_offset` = how much of a file an interrupted upload left), answered by `FsResponse`. Data travels as for "Send files", on unidirectional streams of `FileChunk`, now carrying `transfer_id`, destination `dir` and `offset`; downloads use streams from the agent.
- **Resume**: the receiving side writes `name.part` and renames it only when complete, so an interrupted transfer leaves the part; "Resume" asks how much is there (upload) or measures it (download) and sends only the rest. A part that does not have exactly the expected size is refused, and nothing beyond the announced size is ever written; a download asked from beyond the end of the file is answered with an error. The destination folder must be a full (absolute) path, and a `.part` that is a link (symbolic link, junction) is refused.
- **As the user**: on the agent of the service (SYSTEM) every file operation runs on a thread that impersonates the user signed in on the PC (`ImpersonateLoggedOnUser` with the session token): the person in control sees and writes only what that user could. Without a user signed in it is not available.
- Automated tests: `nuvira viewer --download REMOTE_FILE --download-dir DIR` and `--upload FILE --upload-dir REMOTE_DIR`, with `--resume`; the viewer exits when the transfers are over.

Tests of 2026-10-27, NUC → PC-LABORATORIO (service) through the NAS server: 30 MB upload (same SHA-256; the file is owned by the user, not SYSTEM), upload resumed after 10 MB already there, 25 MB download, download resumed after 8 MB, the service configuration (readable only by SYSTEM) refused with "access denied"; window with both panes opened from the toolbar.

## Copy and paste of files (2026-11-15)

Files and folders copied on one computer (Explorer, Finder, Nautilus, Nemo, Dolphin…) can be pasted on the other, in both directions, with the usual keys or menu. The list goes to the other side at once; the contents travel only when something pastes them, so copying a large folder costs nothing until it is pasted.

- **Protocol** (`session.proto`): `Hello.clipboard_files` on both sides (the viewer always, except terminal-only sessions; the agent when it controls the PC and neither the clipboard nor files are turned off). `ControlMessage.clipboard_files` carries the list (`ClipboardFiles`: a number for the copy and the entries, with relative "/"-separated paths, sizes, folders, modification times; folders before what they hold, at most 10,000 entries, links skipped). A paste asks for one file of that list by its index (`ControlMessage.clipboard_file_request`, with an offset); the answer is a unidirectional stream of `FileChunk` with `clipboard_file` set (`error` set when the file cannot be read). Requests name an index in the current list only: the other side cannot read anything that was not copied. A list older than the latest is refused.
- **Permissions**: the agent offers and serves files only while the session's "clipboard" and "files" switches are both on (`32-session-permissions.md`). Turning one off forgets the list copied here and takes the other side's files off this clipboard (an empty `RemoteFiles`, written like any content: Windows empties the clipboard if its object is still there, Linux lets the selection go and unmounts, macOS clears the pasteboard if it still has the placeholders); the viewer does the same when the agent tells it they are off. A paste then pastes nothing instead of failing half-way; copying again after the switch is back on works. As SYSTEM (Windows service) files are listed and read as the person signed in.
- **Windows** (`client/clipboard/src/win_files.rs`): the other side's files are an OLE data object (`FileGroupDescriptorW` + `FileContents` as one `IStream` per file, fetched on the first read, `Preferred DropEffect` = copy, asynchronous copy supported), on a thread with its own message queue. Explorer shows its usual progress and "Replace or skip" questions. As SYSTEM, the process allows calls from the session's user into it (`CoInitializeSecurity`), and since a SYSTEM process does not see what Explorer copies (only its OLE object), it reads the clipboard with a helper started for a moment as the person (`agent --clipboard-files`, `client/agent/src/clip_user.rs`).
- **Linux** (`client/clipboard/src/x11_files.rs`, `fuse_files.rs`): the X11 CLIPBOARD selection, through XWayland on Wayland (Mutter and KWin pass it on to Wayland programs), with `x-special/gnome-copied-files`, `text/uri-list`, `UTF8_STRING`. The paths handed over are in a read-only FUSE file system of ours, mounted without root through `fusermount3` (`fuser` crate, no libfuse) when files are first offered, at `$XDG_RUNTIME_DIR/nuvira/paste/<pid>` (it takes no space; the runtime folder is emptied at sign-out), one folder per copy (the last 4 stay readable, so a paste still running when something else is copied finishes). The answer is immediate; a file's contents are asked of the other side while the file manager reads it (from the offset read, so a jump restarts there). Answering only once everything was fetched does not work: Mutter cancels any XWayland ↔ Wayland clipboard transfer after 15 s (`meta-selection.c`) and Qt waits 5 s on X11, so a large paste failed on GNOME Wayland. The mount is undone when the session ends (tried: GNOME, at the session's end); one left by a process that was killed (`kill -9`, or SIGTERM: the agent does not catch it) stays, unreadable, until the next start of the agent or viewer (`fusermount3 -u -z`, tried) or sign-out. Without FUSE the old way stays: requests within 700 ms of the offer (file managers read the clipboard as soon as it changes owner) are answered with the planned paths, the first later one fetches everything into `~/.cache/nuvira/paste/<pid>` (mode 0700) and names those.
- **A new copy of the same files** is sent again (a session started after the copy, or the same files copied twice): Windows from the clipboard sequence number, macOS from the pasteboard's `changeCount`, Linux from XFixes events on the CLIPBOARD owner (an X connection of its own). Without them only different files count.
- **macOS** (`client/clipboard/src/mac_files.rs`): Finder does not paste file promises (they are for drag and drop), and a pasteboard data provider must answer synchronously on the main thread. So, as RustDesk does, the pasteboard gets empty placeholders with the copied names (in `~/Library/Caches/com.nuvirahub.paste/<pid>`), each with the extended attribute `com.nuvirahub.paste` (token of the copy and entry index). Finder pastes them like any file, with its own questions about names already there, and keeps the attribute; an FSEvents stream on the home folder and `/Volumes` (file events, on a dispatch queue, ignoring this process's own changes) notices the copy and fills it: the file's contents or, for a folder, everything in it, with the modification times; the attribute is removed at the end. A file not received whole is removed. Writing into Desktop, Documents or Downloads may ask the person at the Mac for the permission once (macOS privacy).
- **Not possible / limits**: on macOS a paste into an app other than Finder gets the empty placeholders; a paste outside the home folder and `/Volumes` is not filled. Links are not copied. The web client has no file copy and paste (browsers do not allow it).
